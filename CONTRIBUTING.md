# Contributing to Cadenza

Cadenza welcomes narrowly scoped, evidence-backed improvements once a project
licence is present at the repository root. If `LICENSE` is absent, pause before
submitting code: contribution and redistribution terms have not yet been
established.

## Development environment

Use Windows 11, the .NET 8 SDK selected by `global.json`, Node.js 22, Git, and a
WebView2 Runtime. Visual Studio 2022 is optional. A MIDI controller is not
required for build or automated validation.

```powershell
git clone https://github.com/RJCHAN21/Cadenza-development.git
cd Cadenza-development
./scripts/Validate.ps1
```

The validation command must pass from a clean worktree. It restores and builds
`Cadenza.sln` in Release mode and runs the same fixture, parser, simulation, and
renderer checks as CI.

## Branches and pull requests

- Branch from the current default branch and keep one coherent concern per PR.
- Do not commit `bin`, `obj`, local profiles, diagnostics, private scores, or
  package caches.
- Keep changes focused; avoid unrelated formatting or architecture rewrites.
- Explain the observed behavior, root cause, solution, and validation evidence.
- Add or update a regression whenever behavior changes.
- Maintainer review is required before merge. Contributors do not merge their
  own change unless separately authorized by project policy.
- Preserve fast-forward-friendly history; do not force-push after review has
  begun without coordinating with the maintainer.

## MusicXML compatibility reports

Do not upload a commercial or personally obtained score unless you have clear
permission to redistribute it in a public test suite. Reduce the behavior to a
small original MusicXML example containing only the structures needed to
reproduce it. State the expected written measures, repeat/ending traversal,
performance occurrences, and beats so the assertion is independently
justified.

Fixtures must:

- be original, public-domain, or under a compatible redistributable licence;
- document source and licence/provenance;
- avoid names, lyrics, melodies, or metadata from copyrighted songs;
- be deterministic and generated by a checked-in script when binary;
- cover the smallest meaningful parser or navigation boundary.

## Regression evidence

Run `./scripts/Validate.ps1` and include its concise final result in the PR.
For UI, WebView2, MIDI, or audible-output changes, also document the manual
Windows environment, device/runtime versions, reproduction steps, and result.
Screenshots and recordings are useful supplements but do not replace an
assertion over authoritative state.

## Code expectations

- Treat warnings as errors and keep nullable analysis enabled.
- Preserve the written-beat/performance-beat distinction described in
  `docs/ARCHITECTURE.md`.
- Bound data read from MusicXML, MXL, MIDI, WebView messages, and local JSON.
- Do not add telemetry, cloud accounts, advertisements, proprietary catalogues,
  or engagement mechanics without an explicit project decision.
- Never describe heuristic note matching as professional assessment or proven
  educational guidance.
